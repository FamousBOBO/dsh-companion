# Prompt 分层后续项

本文件记录 **P1–P4 期间发现、但按计划范围没有修** 的问题。每条都写明证据、根因、
为什么不在本次范围、以及修的时候要注意什么。

> 下文引用的输入与回复全部来自**构造的合成样本**（`tmp/p5-capture.mjs` 里的固定句子），
> 不是用户的真实聊天记录，也没有复制任何私人记忆内容。合成的意义只是让缺陷可复现。

## 1. task 档回复正文为空（P5 抓包发现）

**证据**：`session-9bb3dd3b` 第 6 轮，输入「用一句话解释一下什么是幂等」，
`assistant/message` 只有 `reasoning` 块（64 字，含完整答案），`text` 块为空。
用户看到的是空白回复。

**根因**：task 档注入的写法模块合计 247 字，其中没有任何一条要求"答案必须写在正文里"。
`thinking.guided` 的正文是「思考过程不外露，正文只给结论和他用得上的细节」——
模型把"不外露"理解成"放进 reasoning 就够了"。

**为什么不在本次范围**：这是写法模块设计问题，不是 P1–P4 的任何一处改动引入的。
改动前的 `thinking.guided`（62 字）同样没有这条要求，抓包基线里没有 task 档样本，
所以之前没暴露。修它需要改模块正文并单独做 A/B（模型行为对这句话很敏感），
属于计划 §5.4「动态模块减重」之外的**新增约束**，不该混在清理里悄悄加进去。

**修的时候注意**：

1. 不能只加"答案写在正文"，否则会让 roleplay 档也变成"先解释思路"——那条只该在 task 档生效；
2. 需要在 `prompt-lint.mjs` 之外加一条检查：`assistant/message` 的 `text` 为空但
   `reasoning` 非空 ⇒ 记为一次"空正文"，可用于回归；
3. 如果确认这是该模型（`deepseek-v4.1-flash` + effort high）的固有倾向，
   应该在 `mode.task-frame` 里写正面要求（"正文直接给结论"），而不是写负面禁止。

## 2. 思考过程漏进正文（P5 抓包发现）

**证据**：同一会话第 5 轮，`implicit-roleplay` 档，`text` 块开头是
「他在问"如果那天我没走…"，带点感伤…我不该编造共同经历…语气：有点认真」，
之后才是真正的回复「留啊 / 不过"那天"是哪天，你得说清」。

**根因**：与 §1 同源。`style.universal` 只有一句"不编造现实事实与共同经历；不确定就说不知道"，
没有任何一条说"不要把你的分析写进回复"。

**为什么不在本次范围**：同上。而且这条与「像人聊天」高度耦合——一旦措辞过硬，
普通聊天的自然度会下降，必须 A/B。

**修的时候注意**：

1. 最省的做法是把它并入 `style.anti-ai-chat`（它已经是"像人聊天"的唯一归属），
   而不是新开一个模块；
2. 别写"禁止输出思考过程"——模型会改成另一种元叙述（"我这样回是因为…"）；
   写正面要求更稳："直接说你会说的那句话"；
3. roleplay 档同样需要，但措辞要与 `style.roleplay-narrative` 的白描要求一致。

## 3. chat 档动态写法 404 字，未达计划 §5.4 的 250–350 目标

**现状**：404 字（8 个模块：32 + 31 + 54 + 51 + 30 + 54 + 119 + 26 + 7 个连接换行）。
改动前 512 字，已降 21%。

**为什么停在这里**：剩下能压的只有 `style.anti-deepseek`（119 字）与各档的 `mode.*` /
`operator.*`（每条 50–65 字）。再往下压就必须删整条规则，而每一条都对应一个真实缺陷：
- `anti-deepseek` 点名的 8 类套话（对偶句、微微/一瞬/一拍、抽象比喻、动作后解释情绪、
  连续并列短句、段尾强行总结、固定转折词）是 DeepSeek 的高频特征，删掉就失去降频依据；
- `operator.dig` 与 `operator.review` 分别在 chat 档承担"听懂意图"与"自检"，
  删掉等于放弃 DIG/REVIEW 算子在该档的作用（合同 §4.2 明确 chat 档这两个算子为 on/optional）。

**结论**：把 404 当作首轮实验值，并把测试上限钉在 450 防止长回去（`prompt-modules.test.mjs`
里的 `chat 档全部模块合计 ≤450`）。真要继续压需要先改合同里的算子表，不在清理范围。

## 4. `prompt-lint.mjs` 只统计、不拦截

**现状**：它统计套话出现次数，不修改模型输出。这是设计选择（降频而非禁词替换），
但意味着**没有自动化质量闸门**：注入变短之后，套话是否变多只能靠人工看抓包。

**后续**：如果要加自动化，应该加在"回复质量"侧而不是"提示词"侧——
例如对一批固定输入跑 N 次，统计 `微微/一瞬/不是…而是…` 的出现率，超出阈值就报警。
这需要真实模型调用预算，本次没有做（计划 §1.2 禁止未经授权的付费调用）。

## 5. Persona 仍是 4,797 字，占 System Prompt 的 81.5%

**现状**：按计划 §5.1 一字未改。精简建议与示例见 `docs/persona-simplification-example.md`，
应用与否由用户决定。

**注意**：一旦用户应用优化，System Prompt 会降到约 3,300 字（低于计划 §7.3 的 4,000–5,500
候选区间下限）。那时应该重新评估"是否删得过多"，而不是庆祝更短——
计划明确写了区间是**候选目标**而非硬门槛。

## 6. 独立语义路由仍然不存在

`docs/11-prompt-routing.md` §1 已如实记录：现在的路由是规则路由，不是模型分类器。
如果以后要做，按计划 §6.2-4 必须先写 RFC，评估"同次主模型自由选择写法"是否已经够用，
不要把分类器偷偷塞进清理计划。

## 7. `npm run verify` 的 unit 组需要 `DSH_COMPANION_PERSONA_ID=bot`

**现状**：本 worktree 的 `config/suite.json` 里 `persona.id` 是复制生产环境时带来的旧值，
而多个模块的测试 fixture 断言的是模板默认值 `bot`。因此直接 `npm run verify` 会有 3 个模块报红，
设 `DSH_COMPANION_PERSONA_ID=bot` 后 9/9 通过。

**为什么不在本次范围**：`config/suite.json` 是用户资产（gitignore），计划 §1.2 禁止改它。
这是**本地测试环境**的既有状况，不是本次改动引入的。

**后续**（如果要彻底解决）：让测试 fixture 从环境变量或 fixture 自己的 suite.json 读 persona id，
而不是依赖仓库根的本地配置。这属于测试基建，应该单独一个 PR。
