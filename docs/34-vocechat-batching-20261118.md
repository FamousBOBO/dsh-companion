# 2026-11-18 VoceChat 入站攒批与分段停顿（对齐 QQ）

同一件事分两条消息发过来时，她要么答两遍、要么只答第一句 —— 这是"一条条答得很碎"的来源。
QQ 那条通道早就有 `DmBuffer`，VoceChat 这条没有：每条入站事件**立刻**驱动一轮回合。
本轮把攒批与分段停顿一起补上，参数直接照抄 QQ 已经用真实聊天调过的那一组。

证据级别：本机部署 + 真实平台消息往返（见第四节）。

---

## 一、缺的是什么

`vc_message` 的发送方向用 `segmentText()` 拆段（回复会分成几条连续消息），但**接收方向没有对称机制**：

| | QQ 通道 | VoceChat 适配层（本轮之前） |
|---|---|---|
| 入站合并 | `DmBuffer`：安静窗口内合并同一段话 | 无，每条事件一轮 |
| 窗口随长度变化 | 短句 6s / 长句 1.5s 插值 | — |
| 总等待上限 | `dmMaxWaitMs` 15s | — |
| 攒满提前 | 条数/字数触顶立刻处理 | — |
| 出站分段停顿 | `delayPerCharMs` 60ms/字 | 无，几段同一瞬间发出 |

后果在真实聊天里看得很清楚：主人打「在吗」「问你个事」「昨天那个文件你放哪了」，
她回了「在的」然后停在那里 —— 第三条才是真正的问题，但它到的时候第一轮已经在跑。

出站那一半同样不像人。`sent-log` 里三条回复的 `at` 相差 4–10 毫秒：

```json
{"at":1794987354207,"segment":1,"of":3,"preview":"侧栏长什么样我可看不到，我只管收发"}
{"at":1794987354228,"segment":2,"of":3,"preview":"从我这边看，消息一条没漏，你都收到了"}
{"at":1794987354232,"segment":3,"of":3,"preview":"所以应该没问题喽"}
```

## 二、入站攒批（`buffer.mjs`）

三条判据，每条对应一个具体坏结果：

1. **短句等得久、长句等得短。** 三个字多半还有下文（6 秒）；已经八十个字基本说完了（1.5 秒）。
   按字数在两者间线性插值。
2. **总等待有上限。** 从**这一批第一条**算 15 秒。没有它，一个持续说话的人能把窗口无限推后，
   她就永远不开口 —— 这是"加了缓冲之后反而不回消息"的经典成因。
3. **攒满立即发。** 8 条或 4000 字触顶就不用再等安静。

放在 `queue` **之前**是有意的，两层管的事不同：

- 缓冲决定「这一批消息什么时候算说完」
- 队列决定「什么时候真的能跑」（同房间串行、全局并发、上限）

反过来的话，队列会把每条消息先排成一串任务，缓冲再合并也只是把已排的任务并起来。

三个必须做对的细节：

- **去重是全局 mid 集合。** VoceChat 的 mid 是平台级自增（不是每会话独立），SSE 断线重连会重投
  同一段帧。QQ 用每会话集合是因为 OneBot 的 message_id 语义不同。
- **交付期间进来的消息自己开新窗口**，不并进正在跑的那一批（否则"她正在答第一件事"时补的
  那句话会被塞进上一轮，等于没听到）。
- **交付抛错就把这一批放回队列**并重新排期。内容不许丢 —— 与 QQ 的 `unshift(...lines)` 同一取舍。

交给模型的提示词也分两种（`inboundBatch`）：

- 一条时与旧的 `inboundLine` **逐字节相同**（单条消息的提示词不该因为加了缓冲而改变）
- 多条时逐条带 mid 列出，末尾明说「这几条是同一段话的几句，按整体回应一次，不要逐条各答一遍」

## 三、分段停顿（`pauseFor`）

按**刚发出去那句**的字数计时：长句说得久、下一句自然来得晚；一句「嗯」之后几乎立刻接上。

默认 60ms/字、下限 200ms、上限 3000ms（与 QQ 的 `COMPANION-QQ-PATCH-5` 同一组数）。

上限必须有具体理由：一句 200 字按 60ms/字要停 12 秒，回合会被 `turnTimeoutMs` 掐掉，
用户看到的是"发到一半不说了"——比不等更糟。

`delayPerCharMs: 0` 退回旧行为（同一瞬间刷出几条），配置可关。

## 四、实测

### 4.1 三条消息合成一轮

连着发「在吗」「问你个事」「昨天那个文件你放哪了」（间隔 1.2 秒），`sent-log` 里只有**一条**
`turn-start`，且带着这一批的全部 mid：

```json
{"kind":"turn-start","room":"vc-dm-1","mid":664,"resumed":true,"mids":[662,663,664],"batched":3}
```

回复是对整段话的一次回应（4 段），不是三次各答一句。

### 4.2 分段有了人的节奏

```
seg 1/4     0ms  «在啊»
seg 2/4   218ms  «不过…»
seg 3/4   224ms  «哪个文件？»
seg 4/4   317ms  «我翻了翻，昨天我这边就动过几个零碎的小记录，没见着什么要紧的东西»
```

改之前是 4–10 毫秒连续刷出。现在短句停在下限 200ms、长句按字数拉长。

### 4.3 生效参数可查

```
[vocechat-adapter] batching: on 短句6000ms/长句1500ms(80字) 总上限15000ms 满8条或4000字
[vocechat-adapter] 分段: on style=active 最多6条 间隔60ms/字(下限200上限3000)
```

这一行不是装饰：默认值不等于部署值（profile 会整段替换插件自带的 `config`），
"为什么她等 6 秒才回"必须先能查到是哪一组数字在起作用。

## 五、测试

`plugins/dsh-vocechat-adapter/test/buffer.test.mjs`（16 项）用可控时钟与定时器，
每一条都钉住一个**具体坏结果**，而不是"函数返回值对不对"：

- 三条短句合成一批；每来一条推后窗口，但 15 秒硬预算到了必发
- 长句按 1.5 秒交付；条数触顶/字数触顶立刻交付且不残留定时器
- 同 mid 只收一次；两个房间的 mid 不互相顶掉；两个房间的窗口互不推迟
- 交付失败把这一批放回并重试（内容不丢）；交付期间新到的消息不并进正在跑的那批
- 销毁时收掉定时器并报出未交付条数（不静默丢）

`test/pause.test.mjs`（7 项）：按字数计时、上限兜住超长句、0 值关闭、emoji 按字符计。

`test/inbound-batch.test.mjs`（7 项）：单条与旧提示词逐字节相同、多条带 mid 且要求整体回应、
正文换行缩进保留。

全部：`vocechat-adapter` 165 项通过，`channel-vocechat` 116 项通过。
