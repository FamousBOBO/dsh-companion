# 点歌翻唱（B站 → RVC 音色 → QQ 副歌语音条）

> 这份文档解释**这条链路为什么这样设计**。可执行的部分在
> `plugins/dsh-channel-qq/src/features/song/`（业务）与
> `plugins/dsh-channel-qq/src/adapters/song/`（外部世界）。
> 证据等级记在 `docs/07-verification-status.md`，本文不重复声称验证。

## 1. 一句话

私聊里说「唱一下《晴天》」，机器人去 B站 找原唱、下载音轨、找出副歌、
用机器人自己的音色模型翻唱，然后把**副歌那一段**发成一条 QQ 语音条。

## 2. 四步与每步的产物

| 步 | 做什么 | 产物 | 失败算谁 |
|---|---|---|---|
| 1 `downloading` | `x/web-interface/view` → 分P → `playurl` → 取音轨 → ffmpeg 转 wav | `audio.wav`（44.1 kHz / 立体声 / pcm_s16le） | B站适配器抛，队列记 `failed` |
| 2 `chorus` | `tools/song/find_chorus.py`：重复段落 + 人声活跃 + 人声起点对齐 + 人声句尾 | `{start, end, confidence, method, phraseEnds}` | 定位不可靠 → `SongStepError('chorus')` |
| 3 `covering` | `make_cover.py`：MelBand Roformer 分离 → March7 RVC → 混音 → 裁语音条 | `voice.mp3`（≤59 s，收在句尾，44.1 kHz） | 任一步非零退出 / 超时 → `failed` |
| 4 `sending` | 闸门 → `record` 语音条（**恰好一次**） | 平台回执 `message_id` | 回执未知 → `unknown-send`（禁止重发） |

**顺序不可换**：副歌要**整条**音轨才能判断"这段旋律重复了几次"；翻唱要**副歌起点**
（否则切出来的片段不知道从哪截）；发送要**成品**。

## 3. 五条刻意的取舍

### 3.1 只跑副歌附近的片段，不跑整首

`make_cover.py` 每一步按时长线性涨。本机实测（RX 6700 XT / DirectML）：
karaoke 分离对 320 s 的歌约 **89 s**，模型 B 对 45 s 片段约 **27 s**。
整首跑一次两分半以上，而语音条最多 59 秒——需要的是副歌那一段。

所以先切 `[chorusStart - 12 s, chorusStart + seconds + 10 s]`，交给 `make_cover.py`
的是一个 40–50 s 的 wav。**12 秒前置余量**是给分离器的：从副歌正起点开始切，
第一句常被判成人声不活跃，伴奏就漏进人声模型（实测压到 2–3 s 时糊得明显）。

### 3.2 副歌定位不可靠时"不猜"

`confidence = 0.45*相似度 + 0.35*人声活跃 + 0.20*重复次数`。低于
`minConfidence`（默认 0.55）时：

- **私聊入口**：不发语音条，回一句"没找准副歌，给我一个时间点或换一条视频"；
  用户给了 `chorusSeconds` 就跳过定位。
- **自主入口**：跳过这一轮，什么都不发。

依据是"猜错一次发出去的是**别人歌**做的翻唱，撤不回"这条必然性。

### 3.3 回执未知 = 终点，不是重试点

发送有三态：`ok` / 确定失败 / **回执未知**。第三种（超时、连接断）意味着
**可能已经到了**——再发一次就是两条语音。所以 `unknown-send` 是终态，
并且和 `sent` 一样算"今天发过"（否则下一轮会再发一条）。

网关**确定**拒收且看起来是长度问题（`looksLikeLengthRejection`）时才缩短重做：
45 s → 30 s → 20 s → 15 s（档位按 59 s 基线排，每一档都比上一档短一大截），
**副歌起点不变**，所以听到的仍然是副歌开头。阶梯走完（或已经短于 10 s）就收场——
网关连 15 s 都不收时，多半不是长度问题，再重做一次翻唱只白花 70 秒。

### 3.3b 收尾落在"一句歌词结束处"，不硬切在上限

`seconds`（默认 59，QQ 语音上限附近留 1 s 余量）是**上限**，不是最终长度。
副歌定位脚本同时给出 `phraseEnds`——人声曲线"下凹再回升"的位置（换气/句间停顿）。
`clipLengthFor()`（`features/song/phrase.ts`，纯函数）在 `[20 s, 上限]` 里取**最长**的
那个句尾，所以成品可能是 46.5 s 而不是 59.0 s。

为什么值得这么做：59.000 s 那个切点绝大多数时候落在半个词甚至一句话中间，听感像被掐断；
换气处本来就是句与句之间的空白，切在那里像一次自然停顿。

判据不平移硬编码阈值：`find_chorus.py` 只在副歌起点后 90 s 视界内，用**这一段自己**的
活跃度分位（p20/p70）算出下凹阈值与高位线，再要求"跌之前 1.5 s 内到过高位（刚才在唱）"
且"跌之后 2.0 s 内回到高位（之后继续唱）"——缺这两条，伴奏里的安静处和副歌收场都会被
误当成句尾。段内起伏太小（清唱/电音）时直接返回空列表，让上层按上限硬切。

两条兜底都**明说**在日志里（"收在句尾：65.5s + 46.5s" / "没找到句尾，按 59s 硬切"），
因为"为什么这条正好 59.0 s"必须能从日志里读出来。用户自己给 `chorusSeconds` 时没有
配套句尾信息，按上限硬切（不猜句子边界）。

### 3.4 男声原曲升高八度；能找女声翻唱就找

这个音色模型是女声。拿男声原唱直接换声，f0 落在男声区间，出来明显偏低甚至破音。

顺序（`features/song/gender.ts`）：

1. 先按用户给的（`歌名 歌手`）搜一次——**这是最准的一次**，不要一上来就加
   "女声翻唱"，那会把原唱挤出前几名；
2. 选出来的那条若是**男声**，再搜 `歌名 女声 翻唱`；
3. 找到了女声版就用它（`keyUp = 0`）；找不到就退回原曲，**升 12 个半音**（一个八度）。

性别判定只用看得见的证据：标题/简介里的字面标记（`女声`/`女版`/`女key`…）优先，
其次是常见歌手名单。**没命中一律 `unknown` 且不升调**——升错了（把女声再升八度）
会变成假音，比不升更糟。

判据细节见 `select.ts::pickFemaleCover`：找翻唱时**门槛不是 80 分**（关键词里没有歌手，
那 35 分拿不到，实机分数落在 55–68），改成"歌名必须命中 + 确定是女声"；多条女性翻唱
同一首歌是常态（实机搜《晴天》一次就有 4 条女声版），取分最高的一条即可；
日语/英文/粤语填词翻唱一律跳过（旋律同、词不同，做成语音条就是外语副歌）。

**升八度只作用在人声**，伴奏原地不动——这是同音级移调，和声关系不变，
所以听感上"还是那首歌"。真机对照：`inst.mp3` 两边 MD5 完全相同，`vocal.mp3`
逐帧基频比 median **+12.00 半音**，`voice.mp3` 时长与字节数不变。

### 3.5 清理是合同

每个任务一个子目录（`workRoot/<taskId>`），结束即删；下载的临时 `.m4s` 在
`finally` 里删。理由：一个 6.7 MB 的残留，点十首歌就是 67 MB，而这些东西
**一律没有复用价值**（要听歌请点歌，不要读中间产物）。

## 4. 两个入口，一条队列

```
qq_song_cover（私聊工具面）─┐
                            ├─→ SongQueue（串行、去重、日上限、清理）
autoPickOnce（主动联系节拍）─┘
```

**为什么必须同一个队列**：两条路径各有各的队列，就必然会各发一条；而且这道链路的
成本是分钟级（分离 + 推理），并发跑会把显卡与磁盘打成瓶颈。

- **私聊入口**：由模型调 `qq_song_cover`。它**立刻**回答"收到啦"，语音条做好才发。
  这条路**不过免打扰/额度**——它是对用户请求的回应，不是主动打扰。
- **自主入口**：挂在主动联系的 `afterTick` 上（经服务袋调 `queue.autoPickOnce()`，
  `features/` 之间不互相 import）。只在**绑定主人的私聊**、只在主动规则允许时发，
  **每天最多 `dailyAutoCap`（默认 1）首**，日键按 `Asia/Shanghai` 算。
  发送前**再查一次**授权/免打扰/绑定（用 `contact.outboundBudget()` 那套共享门控）：
  一首歌要跑两三分钟，判断必须用"发送那一刻"的事实。

## 5. 闸门（三道，与的关系）

| 闸 | 默认 | 作用 |
|---|---|---|
| `enabled` | **关** | 总开关。关着时工具只回"未启用"，不挂任何定时器 |
| `dryRun` | **开** | 全流程照跑（真下载真推理），**不真发**，记 `dry-run` |
| `allowExternalSend` | **关** | 第二道；与 `dryRun` 都放开才可能真发 |

出厂三关：装插件不等于机器人开始自己唱歌并往主人私聊里塞语音条。
这条链路还特别贵（一首 90 秒分离 + 30 秒推理）而且**撤不回**。

自主入口在以上三道之上再加 `contact.outboundBudget()`（免打扰/额度/冷却/授权/绑定）。

## 6. 配置

段名 `song`，后台在「音乐」页。**默认全关**，外部路径空着 = 未配置（不猜盘符）。

| 关键项 | 默认 | 说明 |
|---|---|---|
| `seconds` | 59 | 语音条长度**上限**（10–59）；实际长度取不超过它的最后一个句尾，见 §3.3b |
| `minConfidence` | 0.55 | 副歌定位置信度门槛 |
| `preferFemale` | **true** | 优先女声源；男声原曲再找翻唱，找不到升调 |
| `maleKeyUp` | 12 | 男声升几个半音（一个八度） |
| `prefixSeconds` | 12 | 送进分离器的前置余量 |
| `pythonPath` / `rvcRoot` | 空 | RVC 解释器与仓库；**空 = 未配置** |
| `chorusPython` | 空 | 副歌定位的 python（空则复用 RVC 的） |
| `biliCredentialFile` | 空 | B站凭据（**只给插件内部读**，不进日志/工具返回/后台回显） |
| `workRoot` | 空 | 任务工作目录（空 = `<dshHome>/channel-qq/song`） |
| `downloadTimeoutMs` / `chorusTimeoutMs` / `coverTimeoutMs` / `sendTimeoutMs` | 60 s / 30 s / 4 min / 30 s | 四个阶段各给一个上限 |
| `maxQueue` | 8 | 排太长队的语音条已经过时了 |
| `dailyAutoCap` | 1 | 自主选歌每日上限；**0 = 不限额**（见下） |
| `autoSongs` | `[]` | 自主选歌曲目；**空 = 什么都不发** |

**`dailyAutoCap = 0` 是不限额**，但"不限额"必须同时改一处去重键，否则等于没放开：
自主入口的去重键原本恒为 `auto:<日>:<房间>`，同一天第二首会被队列的 `alreadyHandled`
判成"已经发过"直接丢掉。所以第 2 首起键里带序号（`auto:<日>:<房间>:2`，任务 id 尾随
`-2`），序号来自账本里当天已发数与 `queue.autoUsedToday()`。**额度没放开时键完全不变**，
既有账本与去重语义因此不受影响。

不限额的代价要写明白：**成本不封顶**。一首歌是 1–2 分钟分离 + 推理，且这条链路串行；
真正兜底的是主动联系那三道闸（免打扰 / 额度 / 冷却）与 `maxQueue`，不是这个字段。

## 7. 部署形态（一个容易漏的坑）

`find_chorus.py` 是**脚本**，`tsc` 不会把它编进 `build/`。而 `chorusScriptPath()`
是从 `build/lib/features/song/` **逐层上溯**找 `tools/song/find_chorus.py` 的：

- 开发机上第 4 跳命中仓库根的 `tools/`，所以本地**永远全绿**；
- 发布包只有 `build/` 与源码，`npm pack` 的 `files` 与 `deploy/pack-release.mjs`
  的 `INCLUDE` 都**不带** `tools/`——装到服务器上第 4 跳落空，副歌定位每条都失败。

修法是让**发布物自洽**：`scripts/build-tools.mjs` 把 `tools/song/*.py`（只 `*.py`）
复制到 `build/tools/song/`，`npm run build` 里已经是第三步。这样 `build/` 一棵树
自带脚本，不依赖仓库根布局，也不会因 `npm pack` vs `pack-release` 走不同路径而漏掉。
`e2e-acceptance.mjs`（真机验收脚本，要 RVC + NapCat）**不复制**，不进发布包。

## 8. 真机验收怎么做

`tools/song/e2e-acceptance.mjs` 跑**真实**的四步（默认 `--dry` 只做不发）：

```bash
# 只做不发：全链路真跑，产物复制到 --keep 供试听
node tools/song/e2e-acceptance.mjs --song 晴天 --artist 周杰伦 --dry --keep out.mp3

# 真发一条语音条（需要 NapCat 环境变量，见脚本头注释）
node tools/song/e2e-acceptance.mjs --song 晴天 --artist 周杰伦 --send
```

它打印逐行的证据：选中的 BV / 性别判定与 keyUp / 副歌起点与置信度 / 语音条时长与体积 /
**平台回执 message_id**（"真的发出去了"的唯一证据）。

**它不进 `npm test`**：`npm test` 里的点歌测试全部用假端口（不联网、不起 python、
不发 QQ），证明的是代码逻辑；证明"这条链路真的能出声音"只能是这个脚本。

## 9. 已知边界

- **同名歌要用户选**：分不出来时返回候选清单让用户给 BV 号。判据是"歌名+歌手是否
  都命中"，不是"前两名分差小"——后者会把"同一首歌的无损/4K修复/UP自剪MV"变成
  一次多余的提问。
- **副歌对齐可能落在副歌前一句**：`find_chorus.py` 的人声起点对齐在"145–175 之间
  人声不间断"的歌（实测 `jay-chou`）上找不到台阶，只能落在平台里。这不是 bug，
  是判据的极限；59 秒里副歌仍然完整。用户不高兴可以自己给 `chorusSeconds`。
- **句尾判据只在一首歌上验过**：`wo_bu_nan_guo` 给出 `70.0 / 74.5 / 82.5 / 85.0 / 101.5 /
  108.5 / 112.0…`，规则取 46.5 s。`PHRASE_*` 那组比例（下凹 45%、高位 60%、回看 1.5 s、
  回升 2.0 s、最小间隔 2.5 s、视界 90 s）是无量纲的，换歌自动跟着段内分位变，但**只测过
  一首**；纯器乐/清唱这类"应该给空句尾"的样本还没在真机上验过。
- **缩短重试仍按档硬切**：网关嫌长时走 45/30/20/15，不看句尾（句尾只在第一次裁剪时用）。
- **B站 `baseUrl` 不一定通**：实机 `ECONNREFUSED` 打在 `*.mcdn.bilivideo.cn:8082`
  上，而同一段音频的 `backupUrl` 一秒能下。所以一条音轨 = 一组地址，逐个试，
  只有"连不上"才换下一条；非 2xx 不换（那是上游说没权限/文件没了，藏起来更糟）。
- **截断的 m4s 比失败更糟**：转出来的 wav 是没结尾的歌，后面的分离/推理会当整首处理。
  所以超上限直接拒，不转码。
- **`seconds` 与 `find_chorus.py --seconds` 两边默认都是 25，但 `chorus.ts` 不传它**。
  哪天有人把 `seconds` 改成 20 或 30，段长与条长会脱钩。要配置化时必须把它透传。
